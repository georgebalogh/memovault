Kafka vs RabbitMQ

2026-04-29 | kafka rabbitmq messaging masstransit
01 Az alapötlet

Ahelyett hogy a kódból közvetlenül hívnád a többi service-t, lerakod az üzenetet egy "postaládába" — mindenki a saját tempójában veszi ki és dolgozza fel.

02 RabbitMQ — okos postás
  • Kézbesít, aztán az üzenet eltűnik (ACK után törlődik, nincs replay)
  • Smart routing: Exchange dönti el kinek megy (direct / topic / fanout)
  • Beépített retry + Dead Letter Queue hibakezelés
  • .NET: MassTransit (saga, outbox, retry mind benne)
✅ email küldés, background job, command queue, saga orchestration
03 Kafka — naplókönyv
  • Eseményeket rögzít időrendben, megmaradnak (pl. 7 napig)
  • Több független Consumer Group olvassa ugyanazt, saját tempóban
  • Replay: visszajátszhatod az összes eseményt (új service, bug fix)
  • Ordering csak partition szinten garantált — partition key tervezés kritikus
  • .NET: Confluent.Kafka (low-level, több boilerplate)
✅ analytics pipeline, event sourcing, audit log, integration event bus
04 Döntési alap
KérdésHa igen →
Kell replay / audit log?Kafka
100k+ msg/sec throughput?Kafka
Több független consumer group?Kafka
Smart routing, DLQ, retry kell?RabbitMQ
Saga / command queue?RabbitMQ
Kis csapat, gyors onboarding?RabbitMQ
Mikor egyiket sem?
  • Egyetlen app, kis forgalom → egyszerű method hívás vagy DB
  • Azonnali válasz kell → HTTP / gRPC
  • Kafka: komoly ops overhead — kis projekten nem éri meg
05 Kritikus .NET hibák
  • Transactional boundary: Kafka publish + DB commit egyszerre → Outbox Pattern kell
  • RabbitMQ retry: NACK + requeue DLQ nélkül = végtelen loop
  • Kafka mint RPC: request/reply Kafka-val lehetséges, de felesleges overhead
Kafka nem helyettesíti a HTTP-t. Ha szinkron választ vársz, ne használd.
